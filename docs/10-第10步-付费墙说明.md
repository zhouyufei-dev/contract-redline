## 1. 我把你写的 `?paid=true` 方案改掉了（原因只有一句话）

**地址栏里的字，是用户可以自己敲的。**

任何人打开 `http://localhost:8501/?paid=true` 都能拿到 20 张卡，一分钱不付。
上线之后这等于"把 20 条深度报告免费公开"，只是需要知道这几个字母而已。

真正的付款证据只有一个：**Stripe 自己在跳转地址后面追加的那串 `cs_...`（Checkout Session id）**。
我们拿这串 id 去 Stripe 服务器问一句"这一单到底付了没有、付了多少"，得到明确的"Yes, $5"才开门。

所以现在的逻辑是：

| 环节 | 具体做什么 |
|---|---|
| 付款成功跳转地址 | `http://localhost:8501/?session_id={CHECKOUT_SESSION_ID}` |
| 我们的动作 | `GET https://api.stripe.com/v1/checkout/sessions/<那串 id>` |
| 判定为"已付款" | `status=complete` **且** `payment_status=paid` **且** 金额 ≥ $1 |
| 判定为"没付/放弃" | 其他一切情况（$0、未完成、乱填的 id）→ 不解锁 |

`?paid=true` 现在只会被当成"没有支付凭据"，一秒钟就被忽略。

## 3. 用户实际会看到的 6 步

1. 上传合同 → 点 **Scan My Contract** → 出报告
2. 标题栏：`1 of 20 cards · the rest is locked`
3. 报告里只有 **1 张卡** —— 自动挑最严重的那条（deal-breaker 优先，其次 serious…）
4. 卡片下方一块黑底面板：`The other 19 are already analysed.` + 分类小标签（还剩几条 deal-breaker / serious / costly）+ 白色按钮 `Unlock the full report — $5`（新窗口打开 Stripe）
5. 付款 → Stripe 跳回 `/?session_id=cs_test_...` → 页面提示 `Payment received: $5.00 USD`
6. 重新上传**同一份**合同 → 20 张卡全开 + 顶部出现下载按钮

## 4. 防刷新、防白嫖：三道锁

1. **付完立刻把 id 从地址栏抹掉**（`st.query_params.clear()`）。刷新时地址栏是干净的，页面回到锁态。
2. **一次付款只换一份合同**：解锁时记下的是这份**文件内容的指纹**（SHA-256），不是文件名。换一份合同指纹不同 → 还是锁着；同一份合同的副本 → 认得出来。
3. **不落库**：解锁状态只活在当前浏览器会话的内存里，服务器磁盘上没有任何记录。

还有个"看不见"的第四道：**锁住的 19 条根本不在发给浏览器的 HTML 里**。
不是用 CSS 藏起来，是压根没渲染。右键"查看源代码"、F12 搜 `R05`、搜 `unlimited` —— 搜不到。

## 5. 你现在必须做的两件事

### 5.1 填密钥（1 分钟）

打开项目根目录的 `.env`，加一行：

```

```

- **必须是 Secret key（`sk_...`）**，不是 Publishable key（`pk_...`）。用 pk 去问会返回 401。
- 先在测试模式（`sk_test_`）走通全流程，最后再换成 `sk_live_`。
- **这串东西只能待在你本机**，不要发给任何人（包括我），不要截图，不要提交到 GitHub。

自查（不会打印密钥内容）：

```powershell
.\.venv\Scripts\python.exe -c "from app.config import get_settings; print(get_settings().describe())"
```

看到 `stripe_key=set` 就对了；显示 `missing` 说明名字拼错或文件没保存。

### 5.2 改支付链接的"成功跳转"（2 分钟）

Stripe 后台 → **Payment links** → 点你这个 $5 的链接 → **编辑** → 找到 *After payment* / *Confirmation page* → 选 **"Redirect to your website"**（不要让 Stripe 显示它自己的成功页）→ 地址填：

```
http://localhost:8501/?session_id={CHECKOUT_SESSION_ID}
```

`{CHECKOUT_SESSION_ID}` 必须用 Stripe 提供的那个占位符（点它给的那颗按钮插入），**手打无效**。
以后有了正式域名，把 `localhost:8501` 换成域名，位置不变。

顺手确认两件小事：
- 这个链接是**一次性付款（one-time）**，不是订阅 —— 我们卖的是"一份合同 $5"，不是月费；
- 金额 `5.00 USD`。

## 6. 这个"最轻方案"的三个真实代价（我不藏）

1. **付完钱要重新上传同一份合同。** Streamlit 从 Stripe 跳回来时是一个全新会话，页面上已经没有你的文件了；没有数据库，就没法在服务器上把"这笔钱"和"那份文件"对上。第二次扫描是秒级的（规则本地跑，AI 解释有缓存）。
2. **按 F5 = 回到锁态。** 这是你要的"防刷新"，代价是：付完钱还没重新上传就刷新，这次解锁就没了（钱还是付了）。补救办法：凭 Stripe 收据发邮件，手动开。
3. **重启服务 = 所有没用掉的解锁作废。** 本地开发时会经常碰到，上线后每次重启也一样。

**要把这三条彻底消掉，只需要一张表**（付款 id ↔ 合同指纹）。你说过这一版不做数据库，所以先不做。等真有人抱怨，再加 —— 那时改动也只是加一个 SQLite 文件，不超过 100 行。

## 11. 排障：密钥填了，但 Stripe 说 401

这段是 2026-11-01 实际踩到的坑，留档。

现象：付款后跳回来，页面红字 `Payments are not being verified right now: the Stripe
key was rejected.`，或者直接 `<h1>401</h1>`。

### 11.1 三步定位（每步都不会打印密钥内容）

```powershell
# 1) 密钥到底读到了没有、是测试还是正式、有没有多余空格
.\.venv\Scripts\python.exe tools\_probe_stripe_key.py

# 2) Stripe 的原话是什么（"Invalid API Key" = 字符串不对；网络类错误 = 另一回事）
.\.venv\Scripts\python.exe tools\_probe_stripe_raw.py

# 3) 是我们的请求头写错，还是这个字符串本身不合法
.\.venv\Scripts\python.exe tools\_probe_stripe_auth.py

# 4) 密钥的"形状"对不对（只显示头 14 位和尾 4 位）
.\.venv\Scripts\python.exe tools\_probe_key_shape.py
```

判定口径：

| 结果 | 含义 | 怎么修 |
|---|---|---|
| `_probe_stripe_key.py` 显示 `configured: False` | `.env` 没被读到 | 文件名是不是 `.env`（不是 `.env.txt`）、变量名是不是 `STRIPE_SECRET_KEY`、改完有没有重启服务 |
| `_probe_stripe_raw.py` 返回 `Invalid API Key provided` | 字符串本身不是有效密钥 | 回 Stripe 后台重新 Reveal + 复制，见 11.2 |
| `_probe_stripe_auth.py` 里 Basic 失败但 Bearer 成功 | 我们的请求头有 bug | 告诉我，我改 `billing._fetch` |
| `raw` 返回 403 / 证书错误 | 网络或代理，不是密钥 | 换网络或代理再试 |

### 11.2 这次的实际原因：把两段前缀粘在了一起

`_probe_key_shape.py` 的输出：

```
masked       : sk_test_rk_liv************************2IgG
total length : 115 (a test secret key is normally 107)
underscores  : 4 -> group lengths [2, 4, 2, 4, 99]
body after prefix: EXTRA UNDERSCORES
```

**真实的密钥长这样，一条连续字符串，除了前缀以外没有任何下划线：**

```
sk_test_51AbCdEf...（共 107 个字符，前缀后面紧跟 51）
```

而 `.env` 里这条是 `sk_test_` + `rk` + `liv` + 再一长串，等于把
`sk_test_`、`rk_`、`live` 三种前缀拼在了一起 —— 这是个**占位/示例字符串**，
不是从 Stripe 后台复制出来的真密钥。Stripe 当然不认。

对照检查两件事：

1. **总长度 107**（`sk_live_` 也是 107）。115 或别的数字 = 粘错了。
2. **前缀后面紧跟 `51`**，而且**中间没有下划线**。出现 `sk_test_rk_` 这种 = 拼接。

修法：Stripe 后台 → Developers → API keys → **Reveal test key** → 全选复制（`Ctrl+A`
`Ctrl+C`，别用鼠标拖选，容易漏字符）→ `.env` 里只贴这一条 →
`STRIPE_SECRET_KEY=sk_test_51...` → **重启服务**（`st.cache` 会记住旧值）。

再跑一次 `_probe_stripe_key.py`，看到这一行才算通：

```
VERDICT: key accepted by Stripe (404 on a fake id, as expected)
```

(404 是**对的**：我们拿一个不存在的订单号去问，Stripe 先验证密钥、再回答"查无此单"。
这就是密钥有效、链路畅通的证据。)

### 11.3 密钥一旦出现在不该在的地方

如果这串真密钥曾发到聊天、截图、提交记录里 —— 立刻去 Stripe 后台 **Roll key**，
旧的作废，换新的。密钥泄漏的代价不是"别人能看你的余额"，是"别人能替你做退款和查询"。

`.gitignore` 里已经有 `.env`，推送到 GitHub 时它不会被带走（部署那一步我会再验一遍）。

## 12. 排障：密钥通了，但支付链接是"正式模式"的

2026-11-02 实测发现的问题，比 401 更隐蔽，因为它**只在付款那一刻才暴露**。

### 12.1 现象

`_probe_stripe_key.py` 通过（`key accepted by Stripe`），但用测试卡 4242 付款时
Stripe 直接拒卡；或者（更糟）用真卡付了 $5，跳回来却提示
`Stripe has no record of that checkout` —— **钱付了，报告没开**。

### 12.2 原因：测试模式和正式模式的链接是两条不同的链接

Stripe 的 Payment Link 分两套，各自独立：

| | 链接长相 | 能用的卡 |
|---|---|---|
| 测试模式（Test mode 开关打开时创建） | `https://buy.stripe.com/test_xxxxxxxx` | 只能用 4242 等测试卡 |
| 正式模式（默认视图下创建） | `https://buy.stripe.com/xxxxxxxx`（**没有 `/test_`**） | 只能真卡，测试卡会被拒 |

判定方法（三个证据一起看）：

```powershell
.\.venv\Scripts\python.exe tools\_probe_payment_link.py
```

它会把三件事摆在一起：密钥模式、链接模式、以及"这个模式的 API 里到底有没有这条链接"。
实测输出：

```
1. key mode          : test
2. link in site.py   : https://buy.stripe.com/7sY00jgD89SQ2bEaXcbfO00
   link mode         : live
3. payment links visible to this key: 0

NOT READY
  - mode mismatch: the key is test but the link is live...
  - this test-mode key sees no payment links at all...
```

关键一条：**测试模式的 API 里支付链接数量为 0** —— 说明那条 $5 链接是在正式模式下建的。
（这就是为什么"后台看着有、代码里也有、就是跑不通"。）

### 12.3 修法：建一条测试模式的链接，并让网站指过去

1. Stripe 后台右上角，把 **Test mode** 开关打开（页面变橙色）
2. **Payment links → + New**（或 Create payment link）
3. 商品名随便写（如 `Contract Redline report`），价格 **5.00 USD**，**One-time**
4. **After payment** → 选 *Don't show Stripe's confirmation page* → 填
   `http://localhost:8501/?session_id={CHECKOUT_SESSION_ID}`
   （测试模式下 Stripe 允许 `http://localhost` 作为跳转地址）
5. 保存 → 复制那条 **`https://buy.stripe.com/test_...`** 的链接
6. 打开 `.env`，加一行（这一步不用改任何代码）：

```
STRIPE_PAYMENT_URL=https://buy.stripe.com/test_xxxxxxxx
```

7. **重启服务**（关掉黑窗口，重新双击 `web.ps1`）
8. 再跑一次预检，看到 `READY` 才算通：

```powershell
.\.venv\Scripts\python.exe tools\_probe_payment_link.py
```

### 12.4 为什么要在 `.env` 里切换，而不是改代码

`site.py` 里的 `DEFAULT_PAYMENT_URL` 就是**正式链接**，永远是它，
`STRIPE_PAYMENT_URL` 只是临时覆盖。上线那天要做的只有一件事：**把这行删掉**（或换成正式的新链接），
网站立刻回到正式收款。改代码的话，很容易出现"上线了还在刷测试链接"这种事故 —— 那就一分钱都收不到。

安全上还加了一道：`resolve_payment_url()` 只接受 `https://` 开头。`javascript:...`
这种值会被当作错误丢回默认链接，不会变成可点击的注入点（`test_paywall.py` 里有用例）。

### 12.5 正式链接也有两件必须做的事

测试通完、切换正式模式时，**正式那条链接同样要**：

- 把 After payment 改成 redirect，地址里带 `{CHECKOUT_SESSION_ID}`（换成正式域名）；
- 确认是 **One-time $5**，不是订阅。

正式模式下这两项如果漏了，用户付完钱会停在 Stripe 的"付款成功"页面，永远回不到我们站 —— 钱收了、报告没给。
